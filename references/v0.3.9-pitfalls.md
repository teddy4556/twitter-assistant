# v0.3.9 轮询 + MutationObserver 改 documentElement — 踩坑

## 问题
v0.3.8 装上后,**用户报告"刷新就失效,要点 900 重设才生效"**。console 报 `userscript.html:905 Uncaught (in promise) invalid name`(油猴 wrapper 内部行号,不是 v0.3.8 代码本身)。

## 根因(经过两轮诊断)

**1.** 用户 console 第二行确认是 v0.3.8:`[tms v0.3.8] 时间轴宽度已更新: 900px` line 814 → 装对了。
**2.** 用户点的 900 触发 v0.3.8 inline setProperty → **这次 inline 写成功了**(因为 menu click 时 DOM 已就绪)。
**3.** 关键差异: **刷新页面后** vs **menu click 触发** 的 DOM 状态不同:
   - 刷新:`@run-at document-start` → 此时 `document.body` 还没解析出来 → `if (document.body)` 假 → 走 `DOMContentLoaded` else 分支 → 等 X SPA 加载完才启动 MutationObserver(很晚)
   - 这中间 `applyInlineWidths()` 早退(`document.querySelector('main div[data-testid="primaryColumn"]')` 返 null) → inline 啥也没写
   - 直到 SPA 加载完 + X 内部 React render + primaryColumn 出现 → MutationObserver 触发 → applyInlineWidths() 终于生效
   - **问题**: X 改版后 DOMContentLoaded 触发很晚,中间存在一个 inline 没生效的窗口
**4.** menu click 时 DOM 早就 ready 了 → `document.querySelector` 立刻返回 primaryColumn → inline 写成功

## 修法(用户拍板 Q1 默认走 轮询)

**v0.3.9 改 2 处**:

### 修法 A:启动后 200ms 轮询,找到 primaryColumn 就停
```js
let _pollAttempts = 0;
const _pollInline = setInterval(() => {
  _pollAttempts++;
  if (_pollAttempts > 25) { clearInterval(_pollInline); return; }  // 5s 后放弃
  const primary = document.querySelector('main div[data-testid="primaryColumn"]');
  if (primary) {
    clearInterval(_pollInline);
    console.log(`[tms v0.3.9] primaryColumn 找到(${_pollAttempts * 200}ms),应用 inline 宽度`);
    applyInlineWidths();
  }
}, 200);
```

**为什么 200ms**:SPA 内部 React render 通常 100-500ms 内完成 primaryColumn,200ms 是平衡值(早触发 + 不浪费 CPU)。25 次 = 5s 兜底,5s 后 SPA 还没渲染 = 异常,放弃轮询。

### 修法 B:MutationObserver 优先 `documentElement` 代替 `document.body`
```js
const _initObserver = () => {
  const target = document.body || document.documentElement;
  if (!target) return;
  new MutationObserver(scheduleWidthApply).observe(target, { childList: true, subtree: true });
  console.log(`[tms v0.3.9] MutationObserver 启动,监听 ${target === document.body ? 'body' : 'documentElement'}`);
};
if (document.body || document.documentElement) {
  _initObserver();
} else {
  document.addEventListener('DOMContentLoaded', _initObserver, { once: true });
}
```

**为什么 documentElement**:`@run-at document-start` 时 `document.body` 通常 null(HTML 还没解析),但 `document.documentElement` 一定有(就是 `<html>`)。监听 `<html>` 一样能 catch 到 X React 后面 mount 的节点。

## 实测验证步骤(用户)

1. 油猴卸载 v0.3.8 → 装 v0.3.9
2. **强刷 X 页面**(Ctrl+Shift+R)
3. console 第一行看到:
   ```
   [tms v0.3.9] loaded — Twitter Media Saver ready. ... 面板宽度: 时间轴=700px ...
   [tms v0.3.9] MutationObserver 启动,监听 body
   [tms v0.3.9] primaryColumn 找到(200ms),应用 inline 宽度
   ```
4. **主栏立刻 700px,无 600→700 闪烁**
5. console 看到 "primaryColumn 找到(200ms)" = 200ms 内找到 + inline 写完

## v0.3.9 vs v0.3.8 关键差异

| 维度 | v0.3.8 | v0.3.9 |
|---|---|---|
| 启动时 inline | `applyInlineWidths()` 单次,无 primaryColumn 早退 | 启动后 + 200ms 轮询 25 次找 primaryColumn |
| MutationObserver 目标 | `document.body`(可能 null) | `document.body || document.documentElement` |
| 刷新后生效时间 | 等 DOMContentLoaded(可能很晚) | 200ms 内立刻 |
| 第二次后(切 tab) | 走 `scheduleWidthApply` 仍然 OK | 仍然 OK,轮询已停 |

## 关键教训
**X 改版后的 SPA 油猴脚本铁律**:
1. **别依赖 DOMContentLoaded**(X 改版后触发很晚,可能几秒后)
2. **别依赖 document.body 在 document-start 存在**(通常还没)
3. **改用轮询**(200ms × 5s)+ **documentElement fallback**(一定有)
4. **轮询找到后立刻停**(CPU 友好,只在 document-start 一次性 5s 内)
5. **后续 DOM 变化靠 MutationObserver**(已经 ready 了)
