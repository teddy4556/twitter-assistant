# v0.2.2 Pitfalls — 阅读位置自动跳转修法

## 问题
v0.2.1.1 用户实测 console:
```
[tms v0.2.1] 找不到 @Arma00554603 /2109768921146589382 (重试 5 次)
```
跳转逻辑已触发,5 次重试 0/500/1500/3000/6000ms 累计 11s 全失败,目标推文不在当前页 article 列表里。

## 根因(3 个,按概率排序)

### 1. 高:重试节奏跟不上 /home 无限滚动
- 推文 lazy-load 平均 1.5-3s,滚到底要 8-15s
- 原版 5 次 11s 太短,根本等不到目标推文进 DOM
- 修法:拉到 7 次 `[0, 1000, 2500, 5000, 8000, 12000, 18000]` 累计 29.5s

### 2. 中:role selector 太严
- 原 `a[role='link'][href*='/status/']`,X 改版后部分 anchor 在 lazy-load 阶段 role 属性丢失
- 修法:严进宽出,role 优先,没 role fallback 到 `a[href*='/status/']`

### 3. 低:目标推文已不在 /home 流(删了 / 私有)
- 修法:重试用尽后列当前页所有 id + 标"含目标 id? true/false" 1 轮定位

## v0.2.2 vs v0.2.1 改动
1. `HIGHLIGHT_RETRY_DELAYS`:5 次 11s → 7 次 29.5s
2. `getArticleTweetId` 兜底 selector 加宽
3. 重试用尽后输出诊断:article 数 / 含目标 id? / 前 5 个 id / 提示分支
4. 所有 `[tms v0.2.1.1]` log tag → `[tms v0.2.2]`(12 处)
5. @version 0.2.1.1 → 0.2.2

## 下次用户给 console 输出时
- 若 `含目标 id=true` → 仍是不严(可能 X 改版更深),进 v0.2.3 进一步放宽
- 若 `含目标 id=false && article=0` → X 改版 article selector,需要重选
- 若 `含目标 id=false && article>0` → 该推文不在流上,正常逻辑(用户滚到目标位置才会重记录)
- 若 article 数 ~3-5:可能没滚,正常
