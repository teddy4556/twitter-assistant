# v0.3.38 — PNG 原图 404 根因(写死 format=jpg 是错的)

日期:2026-10-14 | 触发:用户「twitter助手下载某些资源的时候下载失败」+ 推文链接 `x.com/Fuckyourself1_/status/2110202151461134586`

## 真因(沙箱实测,不是推论)

**X 的 `pbs.twimg.com` 不做服务端转码。`format` 参数只认这张图的「原生格式」,给别的格式直接 404。**

沙箱 curl 实测(pbs.twimg.com 公网可达,不需要登录态):

| 图 ID | 原生格式 | `format=jpg&name=orig` | `format=png&name=orig` |
|---|---|---|---|
| `F84wAzbXYAALzBC` | jpg | **200** (53042B, `ffd8ffe0`) | 404 |
| `F9DOCS0W8AImlRC` | png | **404** | **200** (262135B, `89504e47`) |
| `DfX6HKNXkAA5lkm` | jpg | **200** (52926B, `ffd8ffe0`) | 404 |

完美反相关。**format 必须是原生值**。

### 为什么 v0.3.36 觉得"work 了"

v0.3.36 上线时用 §1.13 段 D 的 `magic` 探针验证,探针取的是页面上**第一张图**。
那张恰好是 jpg 原生 → 200 + `ffd8ffe0` → 判定"work"。

**样本量 1,且恰好落在幸运子集。** 这是 §1.13 元教训的翻版:
探针本身没错,但**样本选择有偏**。凡是"改下载 URL"的验证,探针必须**至少覆盖 jpg/png 各一张**。

## v0.3.37 写死的代码

```js
const baseUrl = (m.media_url_https || '').split('?')[0];
const jpgUrl = baseUrl ? `${baseUrl}?format=jpg&name=orig` : '';   // ← PNG 原图在这里 404
return { type:'photo', ext:'jpg', url: jpgUrl, ... };
```

→ **所有 PNG 原生图(截图 / GIF 封面 / 透明图 / PNG 表情)100% 下载失败,jpg 原生图正常。**
这正好对应用户说的「**某些**资源下载失败」—— 不是全挂,是按格式分。

## v0.3.38 修法

```js
const raw = m.media_url_https || '';
const baseUrl = raw.split('?')[0];
const fm = raw.match(/[?&]format=(\w+)/i);
const fmt = (fm && fm[1] ? fm[1] : 'jpg').toLowerCase();          // 读原生 format
const ext = fmt === 'png' ? 'png' : fmt === 'webp' ? 'webp' : fmt === 'gif' ? 'gif' : 'jpg';
const url = baseUrl ? `${baseUrl}?format=${fmt}&name=orig` : '';  // 只改 name, 不碰 format
return { type:'photo', ext, url, raw, ... };                       // raw = X 原始 URL, 兜底用
```

要点:
- **只动 `name`(→ orig),不动 `format`**。format 是原生标识,碰了就 404。
- **ext 由原生 format 推导**,不再写死 `jpg` → 文件名跟字节 100% 一致,`ffd8ffe0` ↔ `.jpg`、`89504e47` ↔ `.png`。
- v0.3.36 想解决的「ext 写死 jpg 但字节是 png → 双击打不开」问题,**用推导 ext 解决,不需要转码**。转码这条路从根上就不存在。

## 顺带修的另外 2 个静默失败

### 1. `downloadOne` 的 catch 是死代码

```js
try { GM_download({ ..., onerror: (err) => {...} }); }
catch (e) { /* a[download] 兜底 */ }     // ← 永远进不来
```

`GM_download` 是异步 API,**错误只走 `onerror` 回调,不会同步 throw**。
所以 v0.3.7~v0.3.37 那个 `<a download>` 兜底**一次都没执行过**。失败 = 彻底失败,零重试。

**修法**:把兜底搬进 `onerror` 里 —— 第一次失败就退到 `fallbackUrl`(= X 原始 `media_url_https`,X 自己给的,必定有效)重下一次。

### 2. 纯 HLS 视频被静默丢弃

```js
const mp4s = variants.filter(v => v.content_type === 'video/mp4');
if (!mp4s.length) return null;              // ← 只有 m3u8 的视频直接消失
```

用户看到的是「资源少了」而不是「报错」。**修法**:mp4 优先,没有就放宽到任意 `video/*` 或 URL 含 `.mp4` 的 variant,仍然没有才 null。

## 通用教训(跨任务)

1. **改下载 URL 的验证探针,样本必须覆盖多种格式**。取「页面上第一张图」= 抽样偏差的经典案例。
2. **cdn 的 `format=` / `fm=` / `ext=` 这类参数不一定是转换器,常常是「原格式声明器」**。改它 = 改原件 = 404。动手前先测「非原值会怎样」。
3. **异步 API 的 `try/catch` 是幻觉**。`GM_download` / `fetch`(配 AbortController 除外)/ `GM_xmlhttpRequest` 都只走回调。
4. **`filter().length === 0 → return null` 会把失败伪装成「本来就没有」**。用户报「少了资源」时先查这里。

## 复现 recipe(任何 X 媒体格式问题都先跑这个)

```bash
# pbs.twimg.com 公网可达, 沙箱直接测, 不需要登录态
B="https://pbs.twimg.com/media/<MEDIA_ID>"
for f in jpg png webp; do
  printf "%-6s " $f
  curl -s -o /dev/null -w "http=%{http_code} size=%{size_download} ct=%{content_type}\n" \
    -A "Mozilla/5.0" "$B?format=$f&name=orig"
done
```

**哪个 format 返回 200,哪个就是这张图的原生格式。** 三个值互斥,一眼看出原生格式。
